## The TLS question, measured on CRC (read-only)

CRC's import Secret carries caData, taken from `cmapi-system/kube-root-ca.crt` (`deploy/crc-reader-import.sh:16`). The certificates measured are in `r2-outputs/tls-probe.txt` and below:

| Bundle | Holds `CN=ingress-operator@1789448506` (the Route's issuer) |
|---|---|
| `kube-root-ca.crt` (CRC's caData): 6 certificates (4 kube-apiserver signers, `*.apps-crc.testing`, the ingress-operator CA) | **yes** |
| `cmapi/cmapi-trusted-ca`, the injected bundle mounted as `CMAPI_TRUSTED_CA_FILE`: 147 certificates | **no** |
| `cmapi/cmapi-cluster-ca`, the operator ConfigMap | not present (NotFound) |

A TLS handshake to `thanos-querier-openshift-monitoring.apps-crc.testing:443` (the Route is `reencrypt`) gave:

```
head: caData of the CRC import (kube-root-ca.crt), as KubeClient builds it: VERIFIED, TLSv1.3, peer CN *.apps-crc.testing
codex: the pod's CMAPI_TRUSTED_CA_FILE bundle (cmapi-trusted-ca, injected) alone: FAILED SSLCertVerificationError: ... self-signed certificate in certificate chain
codex: trusted_context(injected) incl. this Mac's OpenSSL store: FAILED SSLCertVerificationError: ... self-signed certificate in certificate chain
```

**Ruling.** Head's choice is the right one: the cluster's own trust mode, without the API server's tls-server-name. With it, a caData cluster verifies its Route on OpenShift, because the ServiceAccount CA bundle carries the ingress CA by construction.

Codex's `trusted_context()` breaks the live usage read on CRC and on every caData cluster. Every plan would get `unavailable` and an extra platform approval, and every sweep would be `failed`. It also contradicts docs/02's "one mode per cluster".

The fix never uses `ssl.create_default_context()` and never turns verification off. The insecure mode reaches the Route only where `instance.clusterTLS` already allows it for that cluster's API (docs/02 D1/D2). The same token already crosses the unverified API connection, so this adds no new exposure.

## What Codex missed

1. **Codex's own TLS fix is the outage.** It was measured above: the Route fails verification with the trust Codex chose, on CRC and on any caData cluster. Codex reasoned from the API server's CA, not from OpenShift's ServiceAccount CA bundle, which carries the ingress CA. That carriage is in `manageServiceAccountCABundle`, quoted above.
2. **`thanosUrl` was not validated where it is read** (`load_policies`). The project refuses an `http` apiUrl at parse time (docs/02 "Client rules"). Codex checked only at send time. The final patch does both, and docs/18 says so.
3. **A malformed vector member crashed the plan (HTTP 500)**, not only "looked like a missing sample": the `AttributeError` in `_assemble` is outside the `MetricsUnavailable` catch. It was named in the table only as "can crash assembly", with no test of the plan; the test is added.
4. **The approval facts of a re-render are computed against the tier catalog, not Git.** This is older than this PR (`base/.../pipeline.py:409-410`) and is filed for a follow-up, not fixed here. Measured on head with PostgreSQL (`r2-outputs/logs/probe-catalog-drift.txt`): Git held `requests.cpu: 1` for a tier namespace, and a label-only PATCH rendered `requests.cpu: 8` with:
   - the capacity check delta `(0.0, 0.0)`;
   - `quotaIncreasePct: 0.0`;
   - `usage: None`;
   - no approval slot.

   Codex's H3 fix repairs only the usage read. The capacity delta and `quotaIncreasePct` still read `old_hard` from the catalog.

   **Severity: Medium (pre-existing).** The ruling it needs is whether a catalog change re-approves each namespace at its next render; docs/03's "Tier outdated" facet is the related design. **Proposed fix:** use Git's hard limits as `old_hard` for every quota cmapi renders, with the probe as its failing test. It is not in this patch, because it changes approval semantics outside #310.
5. **Two workers, measured on PostgreSQL 16** (`test_two_workers_run_one_sweep_a_day`, added): two `Worker`s seed the recurring jobs at once and claim at once. The result:
   - one `usage_sweep` ran (`[False, True]`);
   - one `analysis_sweeps` row;
   - one done job with `attempts == 1`;
   - one successor 24 hours out.

   It passes on head as well: the locking is correct. Codex's "source conclusion" now has a run.
6. **Migration 0010, measured on PostgreSQL 16** (`r2-outputs/logs/migration.txt`; script `scripts/migration_0010_roundtrip.py`):
   - empty → head → 0009 → head;
   - 0009 with a `change_requests` row and a `jobs` row → head → (verdict rows written) → 0009 → head.

   The 0009 rows were unchanged at every step. The two tables and their indexes appear and go cleanly. `alembic check` (`test_models_match_migrations.py`) passes. Codex's `idx_sweeps_day` would have needed a migration change for no measured need.

## Backlog (Low, outside the changed lines, no fix)

- The sweep runs every cluster in one transaction (`jobs/usage_sweep.py`). An exception other than `MetricsUnavailable` in one cluster rolls back the others' verdicts for the day.
- With more than seven clusters whose batches all hit the 120-second deadline, a sweep can pass the worker's 30-minute `MAX_JOB_SECONDS`. The lease is then abandoned and a second worker reruns the sweep. The fence rolls the stale run back, but the Thanos work is done twice.
