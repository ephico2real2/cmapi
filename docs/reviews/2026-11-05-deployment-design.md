## D1. Prune and Application layout

**Where they agree (cited).** Both measured the same two things on real Argo CD 3.5.6 and recommend the same layout:
one Application per namespace generated by an ApplicationSet, each child with the resources finalizer and
`Delete=confirm`, instead of one root Application. Opus `logs/e1.log`, `e1c.log`: one pending `Prune=confirm` stops
delivery to every namespace (`team-c created while team-a pends: FALSE after 120s`, controller `Skipping auto-sync:
another operation is in progress`), and one approval releases every delete in that sync operation (`BOTH deleted after
ONE approval`). Codex D1: the same on its own cluster, with the extra observation that an unrelated update (B, `v1`
to `v3`) is also held and released by the one approval. Opus `logs/e1b.log` adds: removing the last folder leaves the
root Application unable to compare (`app path does not exist`, status `Unknown`), so the last namespaces are never
pruned. Both measured the alternative: Opus with a real Git directory generator (`logs/e2*.log`): a removed folder puts
its Application into deletion, nothing goes before approval, a new namespace and a neighbour's change proceed
meanwhile, approving one of two pending removes one; Codex with a list generator: the same isolation.

What each means (measured):

1. **Git unreachable (90 s).** Nothing changes: every Application stays `Synced`, every namespace stays, and the
   ApplicationSet records the error (`unable to resolve git revision`) instead of acting on an empty result. When Git
   returns, all `Synced`. No loss, no action needed.
2. **The ApplicationSet deleted by mistake.** The cascade reaches every child at once: all three Applications go to
   `deleting`, and **no namespace is lost**: `Delete=confirm` holds each one, exactly as on the deliberate path.
   Re-applying the ApplicationSet does not rescue them (45 s later still `deleting`); a person removes the finalizer
   from each, and they return to `Synced` with their namespaces intact. Two consequences for the runbook: (a) recovery
   is one `patch` per Application (`deploy/approve-delete.sh`'s sibling, `deploy/rescue-application.sh`, to write);
   (b) **the window is dangerous**: while every Application is `deleting`, an operator approving any one of them
   deletes that namespace, and the approval looks like a routine one. The approver tooling must refuse when the
   ApplicationSet is absent or when more than one Application of a cluster is `deleting` at once (a deliberate delete
   is one at a time), and `CmapiPruneStuck`-style alerting must fire on "more than one deleting".
3. **A bad merge removing every folder.** In the 60 s the script allowed, nothing happened at all: no Application
   went to `deleting`, no namespace was lost, and the revert found everything `Synced`. That was the script's budget, not a safeguard: run again with a 180 s watch
   (`accident3.py`, `logs/accident3-and-e4.log`), verbatim:

   ```
   [m] commit e1aee818 at t=0
   [m] t=1s apps={'team-a': 'Synced', 'team-b': 'Synced', 'team-d': 'Synced'} namespaces=['team-a', 'team-b', 'team-d'] appset-error='All applications have been generated successfully'
   [m] t=23s apps={'team-a': 'deleting', 'team-b': 'deleting', 'team-d': 'deleting'} namespaces=['team-a', 'team-b', 'team-d'] appset-error='All applications have been generated successfully'
   [m] after 180 s: lost: []
   [m] restored in Git, 45 s later: {'team-a': 'deleting', 'team-b': 'deleting', 'team-d': 'deleting'} ['team-a', 'team-b', 'team-d']
   [m] end: True {'team-a': 'Synced', 'team-b': 'Synced', 'team-d': 'Synced'} ['team-a', 'team-b', 'team-d']
   ```

   So an empty generator result **is** acted on: 23 s after the commit the ApplicationSet deleted every child (the
   controller has no "refuse to delete everything" safeguard; its condition reads success). **No namespace was lost
   in 180 s**: `Delete=confirm` held all three, as in accident 2. Restoring the folders does not rescue the
   Applications (45 s after the revert, still `deleting`: Opus's race finding, `logs/e2-race.log`, holds here); a
   person removes each finalizer and all return to `Synced` with their namespaces. The same dangerous window as
   accident 2 applies, with the same mitigation (the approver tooling refuses when more than one Application of a
   cluster is `deleting`). An ApplicationSet-level guard against this exists only as a policy choice: `applicationsSync:
   create-update` would stop the deletion, at the cost of never deleting a child for a deliberate folder removal
   either (read, `Controlling-Resource-Modification.md`), so it is not taken.

**What `preserveResourcesOnDeletion` and `applicationsSync: create-update` would change (read, `Application-Deletion.md`,
`Controlling-Resource-Modification.md`), and what they cost.** `preserveResourcesOnDeletion: true` makes the
ApplicationSet create children **without** the resources finalizer, so deleting a child (by a removed folder or by a
deleted ApplicationSet) orphans its namespace instead of deleting it: no accident can remove a namespace through the
Application, and neither can a deliberate folder removal. The cost is that the design's delete path (an operator
approves, the namespace goes) no longer exists; a delete would need a person to delete the namespace by hand, which
is the write docs/01 forbids cmapi and asks Argo CD to make. `applicationsSync: create-update` stops the ApplicationSet
from deleting children at all: a removed folder leaves its Application in place, forever `OutOfSync` on a missing path
(Opus measured that state for the root layout: `app path does not exist`, `Unknown`); a deleted ApplicationSet still
cascades through the children's finalizers unless they are also removed. So neither option makes the accident paths
safe while keeping a confirmed delete. What the ApplicationSet deletion accident does need is in the same documents: an ApplicationSet carrying
`resources-finalizer.argocd.argoproj.io` with **background** cascading deletion keeps its Applications when it is
deleted ("You must set the finalizer to ApplicationSet to prevent deletion in such case, and use background cascading
deletion"), and `kubectl delete applicationset --cascade=orphan` does the same for a deliberate removal. **Not
measured** (test: add the finalizer to `e2_set.yaml`, delete the ApplicationSet, confirm the children stay `Synced`
and the namespaces stay; then re-apply and confirm adoption). It costs nothing at sync time, so it goes into
`bootstrap/60-applications/` with that test in PR 3.

**Layout stands? Yes, with two additions.** None of the three accidents lost a namespace on real Argo CD 3.5.6:
`Delete=confirm` on the Namespace held in every case, which is the guarantee docs/01 line 261 feared this layout would
lose. What the accidents cost is recovery work and a dangerous window, so the design adds: (1) an approver tool that
refuses when the ApplicationSet is absent or more than one Application of the cluster is `deleting`, and an alert on
that state; (2) `deploy/rescue-application.sh` to remove finalizers after a mass deletion, with the runbook saying
when; (3) the ApplicationSet carries `resources-finalizer.argocd.argoproj.io` for background-cascade protection
(**not measured**, test in PR 3). Opus's condition for going back to the root layout ("a bad merge or a deleted
ApplicationSet removes a namespace with no approval") did not occur.

**What `docs/01` must change to.** Opus's text for line 261, verbatim, with one sentence added from the accident test:

> **Argo CD.** Each cluster has one ApplicationSet with a git directory generator over clusters/\<clusterId>/namespaces/\*,
> so one Application per namespace, named cluster-configs-\<clusterid>-\<namespace>. Removing a folder makes the
> ApplicationSet delete that Application; its resources finalizer cascades, and the Namespace's Delete=confirm holds
> every object until an operator sets argocd.argoproj.io/deletion-approved on that Application, one namespace at a time,
> with a timestamp later than the deletion. Prune=confirm on the Namespace holds it when a commit removes only its file.
> A single root Application was considered and not used: one pending Prune=confirm stops delivery to every namespace on
> the cluster, one approval covers every delete in that sync operation, and removing the last folder leaves it unable to
> compare (measured, Argo CD 3.5.6). Restoring a folder while its Application waits needs an operator to remove the
> finalizer. Of the accidental paths, measured: an unreachable Git changes nothing; a deleted ApplicationSet puts every Application into deletion but Delete=confirm loses no namespace (a person removes each finalizer; nobody may approve meanwhile); a merge that removes every folder deletes every Application within a generator cycle, and Delete=confirm loses no namespace, with the same recovery.

Line 219 and the `awaiting_prune` row: "waiting for prune confirmation" becomes "waiting for deletion confirmation";
the state machine does not change (both designs agree).

## D3. How a new image reaches the cluster

**Where they agree (cited).** Argo CD watches Git, not registries (both). Image Updater is rejected by both: "under
active development", Kustomize, Helm or plugin apps only, and a Git write credential in the cluster (both read its
README; Opus adds the Source Hydrator for the same reason). Floating tags are rejected (both). The digest is recorded
in Git by Actions after a trusted build on `main`; rollback is a Git revert; the proof compares Argo CD's
`status.sync.revision`, the Deployment's digest, the pod's `imageID`, `/api/v1/version` and `gh attestation verify`
(both; Opus's `deploy/verify-crc.sh` is the script, Codex's four-value record is the same list). cmapi's Application
and the namespaces' Applications are separated by AppProject, source repository and the API server's RBAC (both).

**Disagreements and decisions.**

| Point | Opus | Codex | Evidence | Decision | Reason |
|---|---|---|---|---|---|
