# Round 1 review of cmapi PR #726

**Request changes.** The CRC reader grants and the three rollback commands are correctly scoped. Two Medium findings affect what step 23 certifies. One Low finding affects kind deployments. The proposed [patch](r1-outputs/fix.diff) applies against `head/` and includes regression tests.

## Findings

1. **Medium — the negative SubjectAccessReview can certify a false isolation claim.** At `deploy/crc-proof.sh:230`, the proof asks about `get prometheuses/api` named `user-workload`. Even a cluster-wide binding to `cluster-monitoring-view` has resource name `k8s` in that rule, so the negative answer cannot establish the intended namespace boundary. The user-workload endpoint cited in the justification is `/federate`. Its proxy checks cluster-scoped `get namespaces`, which the reader already holds for its watch cache. The success message and docs/13 consequently claim more than the evidence shows. The patch varies only the namespace in the negative control, rejects an inconclusive SAR, and states precisely which permission was checked. The shell regression exercises an allow on `k8s` in the second namespace, with the correct positive grants present. [OpenShift 4.22 view ClusterRole](https://github.com/openshift/cluster-monitoring-operator/blob/release-4.22/assets/cluster-monitoring-operator/cluster-role-view.yaml) · [User-workload federation proxy](https://github.com/openshift/cluster-monitoring-operator/blob/release-4.22/assets/prometheus-user-workload/kube-rbac-proxy-federate-secret.yaml)

2. **Medium — the reader smoke test can pass while cmapi treats Thanos as unavailable.** At `deploy/crc-proof.sh:233`, the caller uses the workstation CA bundle, omits `partial_response=false`, and accepts the first result without checking the response status or warnings. I passed a successful vector containing a count of 108 and a store-unavailable warning through the two parsers. Head printed 108 and exited 0. The patched proof exited 1. Production rejects warned answers in `cmapi/src/cmapi/capacity/thanos.py:92`. The patch reads the Route as the reader, uses the public CA source that supplies the import, keeps the short-lived token on stdin, requests strict deduplicated results, and requires a clean positive count. The test supplies a positive vector with a warning and checks the CA and query options on the success path. A successful count is a reader access and query smoke test. Per-namespace 14-day coverage is assessed by the application.

3. **Low — the kind comment edit triggers a rollout.** The comments at `deploy/manifests/environments/kind/20-config.yaml:53` are part of a ConfigMap value. The renderer hashes the file bytes. With identical image digests, the API and worker checksum changed from `22f12f8b…` on base to `bac0a443…` on head. Applying head updates both pod templates even though kind still parses `source: none`. Restoring the base file makes the entire rendered kind directory byte-identical to base. This preserves the historical wording of the kind file.

## RBAC and rollback

**Smallest documented platform role — yes.** The `enterprise-4.22` role table says, “Users with this role have the ability to access Thanos Querier API endpoints.” It also lists the core Prometheus and user-defined Thanos Ruler APIs. The broader view role adds user-workload federation access. The CMO `release-4.22` Role limits the rule to `resourceNames: - k8s`, `resources: - prometheuses/api`, and `verbs: - get - create - update` (YAML whitespace folded). A custom GET-only Role could be narrower. The proposed binding uses the vendor-maintained Role in `openshift-monitoring` and names only `system:serviceaccount:cmapi-system:cmapi-reader`. [4.22 monitoring roles](https://github.com/openshift/openshift-docs/blob/enterprise-4.22/modules/monitoring-granting-users-permissions-for-core-platform-monitoring.adoc) · [4.22 metrics API Role](https://github.com/openshift/cluster-monitoring-operator/blob/release-4.22/assets/cluster-monitoring-operator/cluster-monitoring-api-role.yaml)

**Route discovery — required by this configuration.** With no CRC `thanosUrl`, `ThanosQuerier._base_url` reads the named Route to obtain its host. The new Role allows precisely that GET in one namespace. An explicit URL skips discovery. HTTP authorization is a second check. The Route forwards to the web proxy, whose rule names `k8s` in `openshift-monitoring` and specifies `"subresource": "api"`. The proxy maps GET to the RBAC verb `get`. The separate 4.22 service-API documentation also mentions `get namespaces`, already present in the reader's ClusterRole. [Querier Route](https://github.com/openshift/cluster-monitoring-operator/blob/release-4.22/assets/thanos-querier/route.yaml) · [Web authorization rule](https://github.com/openshift/cluster-monitoring-operator/blob/release-4.22/assets/thanos-querier/kube-rbac-proxy-web-secret.yaml) · [HTTP verb mapping](https://github.com/openshift/kube-rbac-proxy/blob/release-4.22/pkg/proxy/proxy.go) · [4.22 service API documentation](https://github.com/openshift/openshift-docs/blob/enterprise-4.22/modules/monitoring-about-accessing-monitoring-web-service-apis.adoc)

**Rollback — confirmed for the three newly deployed objects.** Step 3 checks all three names for collisions. Lines 70–72 of `deploy/crc-rollback.sh` delete both named RoleBindings, then the named Route-reader Role, each in `openshift-monitoring`. No new delete targets the namespace, the Route, the platform Role, or the unrelated broad binding described in the PR record. The rollback identifies objects by kind, namespace and name. It assumes the names checked before deployment still identify this run's objects. Omitting `system:authenticated` from the two positive SARs and checking the binding in the reason avoids counting the unrelated grant as proof. Those restricted SARs describe cmapi's grants only. Real tokens also receive their normal group grants. If several remaining grants authorize the same read, the SAR can report another binding first. Step 23 then stops because it cannot attribute that result to cmapi.

## Behavior when monitoring is unavailable

With the actual CRC config and a transport stub raising `ClusterUnreachable`, I exercised route discovery, the usage adapter, plan facts, approval evaluation and the sweep. The quota-change plan recorded `usage: unavailable`, omitted the peak ratio, and required one `approver-platform` approval. The sweep returned `failed` and both managed-namespace resource verdicts were `insufficient-data`. A successful empty vector or low coverage gives `insufficient-data`. That has different approval semantics from an unavailable backend. The live plan honors its ten-second deadline and can reuse a successful cached result for ten minutes. A missed sweep can leave a previously dated verdict visible. These behaviors predate the PR.

**One scope qualification matters for operators.** The setting belongs to the CRC instance, which can also serve the read-only `KIND_CMAPI_TEST` import. The worker sweeps connected clusters in allowed environments (`jobs/usage_sweep.py:25`). Once that import is connected again, it will try Route discovery there and record a failed sweep on a kind cluster without OpenShift monitoring. Its write policy stays read-only. The patch documents this effect in docs/13. Introducing a per-cluster source selector would change the configuration contract.
