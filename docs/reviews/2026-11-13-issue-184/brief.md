## The change
RFC 9068 section 4: the resource server "MUST verify that the "typ" header value is "at+jwt" or "application/at+jwt"" and reject other values. Before: `Authenticator.authenticate` in `head/cmapi/src/cmapi/core/auth.py` accepted a token whose claim `typ` was `Bearer` or absent, and did not read the JOSE header. After: the header must be `at+jwt` or `application/at+jwt` (case-insensitive) and the claim `typ` must be `Bearer` or absent; with `legacy_token_type` (instance.yaml `auth.acceptLegacyTokenType: true`) the header `JWT` together with the claim `Bearer` passes also. The realm files set Keycloak's client attribute `access.token.header.type.rfc9068` on each client that gets a token for cmapi, and `realm_sync.py` sets it on an existing realm.

## Claims to confirm or refute, exactly

C1. In `Authenticator.authenticate`, the `header` that is checked is the header of the token whose signature was verified: `jwt.get_unverified_header(bearer)` is read before `jwt.decode(bearer, ...)` on the same string, and no path returns an Identity when the signature check fails. Say whether the header check should come before the signature check, and whether its place changes what an attacker learns.

C2. No token that is not an access token of this realm passes in the default mode: a Keycloak ID token (header `JWT`, claim `typ: ID`), a refresh token (HS512 or header `JWT`, claim `Refresh`), a logout token (`logout+jwt`), a token with no `typ` header, a header `typ` that is not a string (a list, a number, null, a dict: `str(header.get("typ") or "").lower()` is the code), `at+jwt ` with a space, `AT+JWT`, `application/at+jwt; charset=x`. For each, say what the code does and whether that is right under RFC 9068 section 4 and RFC 7515 section 4.1.9 (which permits omitting `application/` and says the comparison of media type names).

C3. The legacy mode accepts only the header `JWT` (any case) with the claim `typ` exactly `Bearer`, and never a token with no `typ` claim, an ID token or a refresh token.
