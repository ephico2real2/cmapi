## C1: `typ`, present-and-wrong (Opus) against required (Codex)

**Finding.** Codex: a signed token with the right issuer, audience and time is accepted whatever its type;
require `typ == "Bearer"`. Opus: refuse a present wrong value only; a real Keycloak refresh token is HS512
(refused by the algorithm gate) and a real ID token carries the client as `aud` (refused by the audience
check), so the gap is a synthetic RS256 token with our audience and a wrong `typ`.

**Re-check.** `core/auth.py` now refuses `typ` not in `(None, "Bearer")`; `tests/service/test_review_b_auth.py`
holds the ID and Refresh cases (both measured 401). docs/01 lists "any OIDC issuer" as an Authenticator
alternative; an issuer that sets no `typ` would be locked out by Codex's rule, for no measured gain.

**Decision.** Opus's rule, applied. Codex's stricter rule is recorded as a value a site may want; not built.

## C4: the prune read outage (Codex X5) and the fencing token (Codex X2)

**Finding.** Codex measured on Opus's patch: six failed strict reads in `prune()` exhaust `MAX_ATTEMPTS`; the
worker has no terminal case for `awaiting_prune`, so the job is marked done, the request stays
`awaiting_prune` and the namespace lock is held for ever. Separately: the lease heartbeat is not a fencing
token; a worker paused past its lease commits on top of another worker's claim.

**Re-check.** Codex's test, adapted (`test_prune_read_outage_does_not_exhaust_the_only_job`), failed on the
patched tree with `pending == 0` and passes with its fix: every exception in the read-and-delete block is a
retry with `attempts = 0`; only a successful read that finds nothing confirms the prune. For fencing:
migration `0003` adds `jobs.lease_generation`; `claim()` increments it; `JobRepo.assert_lease()` locks the
row and compares `locked_by` and the generation before the worker's transaction commits, and raises
`LeaseLost`, which rolls the whole transaction back. `test_a_stale_worker_cannot_commit_after_its_lease_was_claimed_again`
fails without the check (the stale event row lands, the job is marked done) and passes with it.

**Decision.** Both accepted and applied (#51, #52).

## C6: `apply` against Argo CD

**Finding.** Both: the deliverer as a cluster-wide writer breaks "cmapi never writes to a cluster directly"
(docs/01). Both agree on three things, applied: `argocd` is the default in the code and the chart; `apply`
fails to render without `delivery.hubDeliverer.acknowledgeDirectWrites`; the default render carries no
`cmapi-deliverer`. Opus adds the `cmapi-deliverer-managed-only` ValidatingAdmissionPolicy, attacked on a
real kube-apiserver (19 denied, 14 allowed), and recommends keeping `apply`, acknowledged, for the CRC thin
slice. Codex recommends OpenShift GitOps for conformance and, failing that, stopping at `merged`.

**Re-check and the tie-break (Fable's recommendation; the owner decides, #63).** Measured on CRC, read-only,
2026-11-05: the OpenShift GitOps operator in the catalog (default channel `latest`, CSV
`openshift-gitops-operator.v1.22.3`; the first draft of this record said "channels gitops-1.10 to 1.14", which was
wrong) supports only the `AllNamespaces` install mode (`oc get packagemanifest openshift-gitops-operator -o json`), so it is a
cluster-wide operator; there is no namespace-scoped way to run its Argo CD. Red Hat's documented defaults for
one instance request 1024Mi (application controller), 512Mi (applicationset), 256Mi (repo server) and 128Mi
each for server, Redis and Dex: about 2.2 GiB of requests before the operator pod
([OpenShift GitOps 1.16, Installing GitOps](https://docs.redhat.com/en/documentation/red_hat_openshift_gitops/1.16/html-single/installing_gitops/);
correction in the second pass: 1.16 is not the catalog's version, 1.22.3 is, and its defaults are unmeasured).
The node has 15525Mi of memory requested (79% of allocatable) and 15860Mi in use (81%): about 4 GiB of
requests left, before cmapi's own 0.6 GiB. A trimmed instance (no applicationset, Dex, HAProxy; controller
request lowered) could request about 1 GiB, which fits, at the cost of a cluster-wide operator the hard
limits ask to avoid and a `Keycloak`-sized workload beside the existing one. `ValidatingAdmissionPolicy` is
served on this cluster (13 policies exist; the first draft said 14), so Opus's containment can be enforced here, unproven on 1.35.

Recommendation: for the thin slice on CRC, `apply`, acknowledged in `deploy/environments/crc.yaml`, with the
policy, and `argocd` proven on the `cmapi-test` kind cluster (Argo CD from its upstream chart, no operator)
before the slice is called done. Reason: it proves every other part of the design on CRC now, without a
cluster-wide operator on a shared node at 81%, and the design's delivery is proven on the cluster made for
tests. Strongest counter-argument, Codex's: the design's rule is a hard rule; a working deviation tends to
stay; a slice proven on `apply` has not proven the design's delivery on CRC; and in `apply` mode the prune
confirmation is enforced inside the worker, so a compromised worker skips it, which only Argo CD's own
confirmation prevents. If the owner can spare about 1 GiB of requests and accept the operator, Argo CD on
CRC is the honest proof, and Codex is right.

**Decision.** The common part applied (#46). The CRC choice is the owner's (#63). Nothing installed.

**The coordinator's decision on #63 (2026-11-05, after the second pass): CRC runs `argocd`, not `apply`.** The
recommendation and the counter-argument above are left as written. `deploy/environments/crc.yaml` selects
`delivery.mode: argocd` and acknowledges nothing; the Argo CD install, the Application, the AppProject and the
repository credential are the thin slice's design step. Nothing of cmapi has run on a real Argo CD, those
objects do not exist on CRC, and the end-to-end walk is incomplete until they do.

## Y5.3: password grants

**Finding.** Opus: `cmapi-cli` allowed the password grant (fixed in the patch); `cmapi-automation` still
allows it for every user of the realm, no fix supplied.

**Re-check.** The design keeps a local automation account (`bot-user`) signing in through
`cmapi-automation` with the password grant (docs/02, docs/08). Making the client confidential means the
grant needs the client's secret as well as a password, so a leaked user password alone no longer mints a
token; the secret is generated into `cmapi-keycloak` (and the import's placeholder Secret). The real answer
for automation is a service-account client, which the design also allows and `svc-payments-ci` shows.

**Decision.** `cmapi-automation` is confidential (#56). `test_automation_client_is_confidential_and_the_cli_is_not_a_password_client`.
