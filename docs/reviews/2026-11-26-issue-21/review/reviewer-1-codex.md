It also accepts a placement claim from a different subject in the same team and a create larger than the placement that passed the zone-loss check. ## Checks against the brief

**Snapshot storage and timing.** The design specifies “30 minutes by default, 15 to 60 allowed” and “one row for the whole cluster, one per zone and one per node role.” The worker registers the recurring handler, floors the observation time, and writes the cluster, zone and recognised role rows. D1 uses the embedded worker, D2 leaves unconfigured Thanos fields null, and D12 lets a multi-role node count in each role. The scheduling correction above concerns the next run's due time. The existing service test checks exact rows, units and alignment. [Stored capacity](head/docs/02-technical-design-v2.md#L956) · [Decision record D1–D13](head/docs/reviews/2026-11-26-issue-21/README.md) · [Job registration](head/cmapi/src/cmapi/jobs/__init__.py#L43) · [Service assertions](head/cmapi/tests/service/test_placement_21.py#L115)

**Concurrency and cap.** The design requires a hold “inside the same transaction as the capacity check, under a per-cluster advisory lock.” Source inspection confirms that property for head. The reserve loop acquires the team/environment transaction lock, counts active unclaimed placements, acquires #725's cluster lock, rereads holds, ranks again and flushes the hold before leaving the session. A direct create takes the identical cluster lock using the submit session. Different teams compete on the cluster lock. The teamless key includes the caller. The cap is three per environment and applies only to unclaimed, active placements. A dry run only ranks. The lock alone cannot repair inconsistent sizing. The namespace-count filter uses the ledger’s current namespace count. Outstanding placements reserve resource quantities only. The patch adds a PostgreSQL mixed-writer test that synchronises a direct create's plan and a placement's initial read before the writes compete. [Design rule](head/docs/02-technical-design-v2.md#L1628) · [Placement transaction](head/cmapi/src/cmapi/plugins/capacity/placement.py#L120) · [Lock key and predicates](head/cmapi/src/cmapi/core/db/repo.py#L419) · [Direct submit](head/cmapi/src/cmapi/core/pipeline.py#L635)

**Reuse, replay and release.** The claim updates only an unclaimed, active placement. A zero-row update refuses submit, rolling back its request insert. Cross-team claims fail the plan's team check. Cross-caller claims require the patch. The create fingerprints the path cluster and the parsed body including `placementId`. A retry by the same subject and key retrieves the original request when the fingerprint matches, even after conversion. A changed body gives 409. This idempotency contract belongs to the namespace write. A repeated successful standalone placement POST can allocate a second hold within the cap. The locked update and create-replay results are source findings pending the service run. [Create and replay](head/cmapi/src/cmapi/plugins/namespaces/router.py#L87) · [Body and cluster fingerprint](head/cmapi/src/cmapi/plugins/namespaces/router.py#L265) · [Claim](head/cmapi/src/cmapi/core/db/repo.py#L468)

A placement expires at 15 minutes by default. The active predicate checks both the release marker and a strict future expiry, so counting stops at the deadline even if cleanup has yet to mark the row. The next reclaim records `expired`. After a committed conversion, the row has the request ID and follows #725's lifecycle release on failure, rejection, cancellation or timeout. If enqueue fails *inside* the conversion transaction, rollback restores the original placement and its original TTL for retry. These are different expected outcomes. The patch adds checks for both. [Expiry and cleanup](head/cmapi/src/cmapi/core/db/repo.py#L428) · [State transition](head/cmapi/src/cmapi/core/db/repo.py#L225) · [Rollback boundary](head/cmapi/src/cmapi/core/db/__init__.py#L44)

**Freshness and headroom.** Docs/02 says “the newest complete snapshot must be no older than two intervals” and defines production zone-failure headroom as “quota headroom computed with the largest zone removed”. On both head and the fixed copy, a focused check admitted a complete snapshot aged exactly 60 minutes at the 30-minute default and excluded one a microsecond older. The 15-, 30- and 60-minute settings all produced a default threshold of two intervals. A newer incomplete run can coexist with an admissible older complete run. The quota watch also needs a good read within its 30-minute relist window. Head checks CPU and memory independently against size × per-resource overcommit − committed − reserved. In the branch's example the largest zone has 6 of 8 cores. A simulated size of 64, CPU overcommit of 2 and commitment of 20 leave 12 cores after zone loss. An 8-core request leaves 4, and a 16-core request fails. One zone leaves zero. The fixed copy handles the coverage, exact-boundary and waited-lock cases above. Two intervals, prod-only checking and a 15-minute hold are defaults. Explicit settings can change all three. [Design arithmetic and freshness](head/docs/02-technical-design-v2.md#L1611) · [Example test](head/cmapi/tests/service/test_placement_21.py#L286) · [Configuration](head/docs/18-configuration.md#L973)

**Selection and score.** Environment scope is resolved before enumeration. Eligible clusters receive one named first-failure reason or a rank. Thus clusters outside the requested environment do not appear by name. The default score weights are 40/25/15/10/10, followed by cluster weight, a cap of 100 and a cluster-ID tie break. D6 specifies the implementation's approximations, including no usage-headroom credit when usage is missing. A successful hold returns 201 and the dry run returns 200. ## Backlog and pre-existing behaviour

- **Pre-existing.** The ordinary pipeline allows a request with genuinely unknown capacity to enter manual approval. A cluster with missing telemetry therefore has no unconditional overbooking guarantee. The fixed D3 path covers clusters with a fresh measured size and known commitment. D13's existing exception for another pending change on the same namespace also remains relevant to ordinary request plans. [Base capacity check](base/cmapi/src/cmapi/core/capacity_backend.py) · [D13](head/docs/reviews/2026-11-26-issue-21/README.md)
- **Pre-existing.** The node counter follows the accepted #302 Ready/cordon/taint policy. It can count a schedulable infra node. Docs/02's phrase “schedulable workers” alone would imply a narrower role filter. [Prior arbitration](head/docs/reviews/2026-11-18-issue-302-capacity/design-capacity-arbitration.md#L32)
- **Low.** The portal can leave a valid hold on a different cluster when the winner changes between Check and Submit. It tells the user to check again. That hold consumes capacity and a cap slot through expiry. Also, preview text says 15 minutes even when the operator overrides the reservation duration. [Portal](head/cmapi-portal-ui/src/portal/NewNamespaceTab.tsx#L492)
- **Low.** In a successful response, the displayed scores and headroom describe the initial ranking instant. Admission uses a later locked read. The response’s `asOf` describes the initial ranking and does not identify the exact headroom at commit. [Placement response](head/cmapi/src/cmapi/plugins/capacity/placement.py#L155)
