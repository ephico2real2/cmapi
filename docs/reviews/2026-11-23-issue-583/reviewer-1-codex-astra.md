## 1. #585 — Valid CA data can disable a cluster import

**Finding.** `head/cmapi/src/cmapi/core/registry.py:301–308` splits on every occurrence of `-----BEGIN CERTIFICATE-----`. An operator can append the explanatory line `Example: -----BEGIN CERTIFICATE-----` to an otherwise valid CA bundle. Head interprets that prose as another certificate and rejects the entire import. Base accepts this case.

This has an observable service consequence. `_check_import` calls `_check` at `registry.py:620–623`. `import_trust` adds `invalid caData` at lines 397–401 and returns no trust at lines 412–413. `_check` sets `invalid-secret` at lines 423–425, before the client factory at line 434 or the probe at line 441. I called `_check_import` with this bundle and a factory that raises if called. Output was `invalid-secret ['invalid caData']`. The real TLS loader is `core/clients/trust.py:95–99`.

**Second finding, same fix.** At `registry.py:303–307`, the code discards everything after the first END in each partition. It only checks the preamble for an unmatched END when there are *no* BEGINs anywhere. A standalone END before, after, or between complete certificates therefore passes. The narrow statement in `head/docs/02-technical-design-v2.md:775` about an END with no BEGIN anywhere holds. The stronger requirement that every END have an open BEGIN does not.

RFC 7468 §2 says “Data before the encapsulation boundaries are permitted”. Sections 2–3 describe boundary **lines**, permit trailing horizontal whitespace, and distinguish explanatory text from legacy encapsulated headers. A `Comment:` line *inside* the encoded data is a different case from an issuer, subject, or example *outside* the block. [RFC 7468 §§2–3](https://www.rfc-editor.org/rfc/rfc7468#section-2)

### Full fix and regression tests

Replace `_valid_ca_data` at `registry.py:294` with the following. It validates each body independently, handles trailing SP/HTAB, and keeps the previous bare-base64 fallback. A boundary mentioned in a sentence never opens a block.

```python
def _valid_ca_data(ca_data: str) -> bool:
    """Validate certificate framing and base64. The TLS client validates the certificates."""
    def decodes(lines: list[str]) -> bool:
        try:
            encoded = "".join("".join(lines).split())
            return bool(base64.b64decode(encoded, validate=True))
        except (ValueError, binascii.Error):
            return False

    lines = ca_data.splitlines()
    body: list[str] | None = None
    found = False

    for line in lines:
        boundary = line.rstrip(" \t")
        if boundary == PEM_BEGIN:
            if body is not None:
                return False
            body = []
        elif boundary == PEM_END:
            if body is None or not decodes(body):
                return False
            found = True
            body = None
        elif body is not None:
            body.append(line)

    if body is not None:
        return False
    return found or decodes([line for line in lines if not line.startswith("-----")])
```

## 2. #583 — Correct weak comparison, with a pre-existing precondition-order defect

**Confirmed for `If-None-Match` alone.** `head/cmapi/src/cmapi/core/etag.py:19,29–42,53–58` consumes the entire list, preserves commas and stars inside opaque tags, recognizes uppercase `W/`, and compares the opaque text case-sensitively. Only a whole-field star padded by SP or HTAB acts as a wildcard. The three callers join field lines in received order at `main.py:262`, `routers/me.py:81`, and `plugins/capacity/router.py:223`. Each has already selected a representation and computed its strong tag.

RFC 9110 §13.1.2 gives `If-None-Match = "*" / #entity-tag` and says the recipient “MUST use the weak comparison function”. Section 8.8.3.2 compares opaque tags character by character regardless of weakness. Sections 5.3 and 5.6.1.2 cover field-line combination and recipient handling of empty list elements. Returning the normal representation for an invalid list is defensible. Section 2.4 permits recovery from invalid constructs without requiring it. [RFC 9110 §13.1.2](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.2) · [§8.8.3.2](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3.2) · [§5.3](https://www.rfc-editor.org/rfc/rfc9110#section-5.3) · [§5.6.1.2](https://www.rfc-editor.org/rfc/rfc9110#section-5.6.1.2) · [§2.4](https://www.rfc-editor.org/rfc/rfc9110#section-2.4)

### Finding — The GET handlers can return 304 when 412 is required

`main.py:259–264`, `routers/me.py:77–83`, and `plugins/capacity/router.py:219–225` evaluate only `If-None-Match`. RFC 9110 §13.2.2 requires an origin server to evaluate `If-Match` first. This applies to GET. The precedence omission predates the PR, but the last row above is a **new observable 304 on head** because the second field line now reaches the comparison. [RFC 9110 §13.2.2](https://www.rfc-editor.org/rfc/rfc9110#section-13.2.2)

**Full fix for these handlers.** Add the following to `core/etag.py`. This uses strict strong comparison for the read-side `If-Match` check and leaves the namespace write API’s special wildcard and unquoted-tag policies alone.

```python
from starlette.datastructures import Headers


def read_precondition(headers: Headers, etag: str) -> int | None:
    match = headers.getlist("if-match")
    if match:
        value = ", ".join(match)
        if value.strip(" \t") != "*":
            tags = _listed_tags(value)
            if not tags or not any(not weak and tag == etag[1:-1] for weak, tag in tags):
                return 412

    if etag_matches(", ".join(headers.getlist("if-none-match")), etag):
        return 304
    return None
```

In each of the three handlers, import `etag_of, read_precondition` from `cmapi.core.etag` and replace the current two-line 304 branch with:

```python
status = read_precondition(request.headers, etag)
if status is not None:
    return Response(status_code=status, headers=headers)
```

## 3. #584 — Folder identity, tag stability, and collision risk

**Confirmed for supported Git folder contents.** `head/cmapi/src/cmapi/core/render/manifests.py:94–103` returns a 64-character hexadecimal SHA-256 digest from `plan_hash`. That digest is the **input** to the outer v1 hash at `core/pipeline.py:112–113`. The v2 outer input at line 110 starts with `folder-v2:`. A v1 outer input therefore cannot equal a v2 outer input, even if a filename or file body literally starts with `folder-v2:`.

Within v1, Git paths contain no NUL, eligible contents contain no NUL, and only an empty content can be encoded as `<deleted>` because the literal marker selects v2. The alternating path/content fields can therefore be recovered unambiguously. Within v2, sorting fixes the order and JSON delimits each path and content independently. Empty folders return the distinct one-character tag `0`.

I ran `print(repr(d), folder_etag(d), plan_hash(d)[:8])` against both trees. Representative outputs follow:

| Folder | Base tag | Head tag |
|---|---|---|
| `{}` | `0` | `0` |
| `{"a": ""}` | `712e6d3669f22641` | `712e6d3669f22641` |
| `{"a": "<deleted>"}` | `712e6d3669f22641` | `048c4431b348b81c` |
| `{"a": "x\0b\0y"}` | `037f7059fa4d27f4` | `5b958cc8ecf89fe3` |
| `{"a": "x", "b": "y"}`, either insertion order | `037f7059fa4d27f4` | `037f7059fa4d27f4` |

| `{"a": "x\r\n"}` | `b7eb2a38f8e60e97` | `b7eb2a38f8e60e97` |

I also compared base and head `plan_hash` directly on the 25 two-file combinations drawn from `None`, `""`, `"<deleted>"`, `"😀"`, and `"a\0b"`. Output was `plan_hash parity True`. The source change replaces the old literal with the same constant. **Normal-folder stability follows from the unchanged computation**, in addition to the measured examples.

**64 bits matter, but the distinction is which collision matters.** Distinct outer inputs can have the same 16-hex prefix, within or across versions. Under the uniform-digest model, matching one specified existing tag has probability \(2^{-64}\) per independent trial. Choosing *both* versions gives the birthday bound. My calculation `sqrt(2*log(2)*2**64)` gave about **5.06 billion versions for a 50% chance of any pair**. Among one million versions the approximate probability of any pair was `2.7105e-08`. A collision between unrelated namespaces does not itself defeat `check_if_match`: `pipeline.py:248–250` compares against the folder for the selected namespace. I found no supported deterministic collision on head and did not establish a practical fixed-target collision. The PR removes collisions requiring no hash search at all.

Two qualifications matter to the scope of that conclusion:

- **Deployment compatibility.** Using the PR’s realistic namespace fixture at `test_validators_583_584_585.py:79–85`, base issued `593d77cc82483bd9` for both empty and literal-marker `extra.yaml`. Head issues that same tag for the empty file and `365756a304ca83a0` for the marker. A client that read the marker on base can therefore submit its old tag after the file becomes empty on head. Calling `check_if_match(old_marker_tag, current_empty_tag, "change")` returned normally in the equivalent one-file probe. This ambiguity is inherited from an already-issued token. Eliminating it would require invalidating at least some ordinary tags, contrary to the requested compatibility rule. The precise fix to the overbroad wording at `pipeline.py:106` is: “Ordinary folders keep their previous tags. Existing tags for exceptional folders must be refreshed and can retain ambiguities from the old encoding during rollout.” The table above supplies both the compatibility and invalidation checks.
- **Python strings versus Git contents.** I refute an unrestricted claim over every possible `Mapping[str, str]`. `folder_etag({"a": "\0😀"})` and `folder_etag({"a": "\0\ud83d\ude00"})` both returned `4c2e134e8e2cfcb0` on head. Default ASCII JSON encodes the scalar and the explicit surrogate pair identically. The latter content cannot be produced by the strict UTF-8 blob decoding at `core/git/workspace.py:317`, `core/git/github.py:77`, or `core/git/gitea.py:76`. I would document the Git/UTF-8 input domain rather than change production tags for an unreachable Python value. Likewise, the folder validator describes the managed Git files. The namespace GET also includes live data at `plugins/namespaces/router.py:233–252`, so folder stability alone does not prove byte identity of that entire HTTP response.
