# Reviewer 1 · cmapi PR #709 · request changes

**PostgreSQL was unreachable.** The sandbox denied TCP to `127.0.0.1:55432` with `EPERM`. Three database-backed cases remain unverified on the patch, including the twelve-request HTTP burst and the successful 202 create. I used the specified PostgreSQL test configuration throughout. ## Decisions on the seven claims

1. **CLI coverage.** Create, change and the three expiry writes, including their dry runs, converge at `Pipeline._plan_namespace`. The other production validation call is `jobs/pr_checks.py:102`, through the worker context's pipeline. Both use the single context-built validator. The two private CLI methods are called only inside `CliValidator.validate`. `test_one_admission_covers_both_commands` checks the slot at both command invocations and counts exactly one admission. Removing all files skips both commands. The policy results route reads `ReportCache`, which lists and watches Kubernetes resources. The cache paging test synchronized six reports using a fake Kubernetes client. The startup exception is fixed above.
2. **Permits and threads.** With integral capacities, admission is a nonblocking acquire. A failed admission owns nothing. Its outer `finally` returns one permit after any successful admission, including a running-slot timeout. Its inner `finally` returns one running permit after any successful running acquire, including an observer exception. Repeated timeouts with the original holder still active distinguish a reusable waiter from a leaked admission. The disconnect test closes an in-process ASGI connection during a check. A second actual request returns 503 while exactly one AnyIO token remains borrowed. After the check finishes, borrowed tokens return to baseline and another hold succeeds. A refused sync request **briefly uses a thread** to reach admission and return the response. The default limits validator occupancy to five threads. It gives no latency guarantee for work before admission.
3. **Worker isolation.** `main.create_app` and `worker.run` build separate contexts. An independent interpreter acquired its slot while the first process held its only slot. `Worker.run` calls one `run_one` per iteration. Busy propagates to the existing job retry/backoff path. The worker-path test held the worker's validator and observed busy before kubeconform. Parsing the shipped plain Deployments gave one API container at **512 MiB / 1 CPU** and a worker in a separate Deployment at **384 MiB / 0.5 CPU**. Helm also rendered distinct API and worker pod templates. One job and one plan consume memory in their respective containers. Both contribute to node pressure. Per-process sizing assumes one server process per API container.
4. **Timeout.** On head an ordinary hung direct child times out and its slot becomes available. The demonstrated failure was a surviving helper. The patch bounds each CLI communication to the existing 60 seconds and kills the invocation's process group on timeout. Two sequential CLIs and an admission wait can exceed the front door's 60 seconds. A client disconnect does not terminate already-running sync validation. The group test covers a helper remaining in the CLI's group.
5. **HTTP and metrics.** A valid plan refused at admission receives `application/problem+json`, status 503, code `validator-busy`, integer `retryAfter`, and the same integer in `Retry-After` via `main.py:257`. Both reasons were exercised through HTTP. Core tests cover rounding up and the one-second minimum. The known metadata 422 keeps precedence. The counter distinguishes `queue-full` and `wait-timeout`. The histogram observes successful plan admissions, including immediate ones. All five checked-in operation examples include the retry header.
6. **Configuration and sizing.** Python Settings accepts concurrency **1–40**, queue **0–40** and finite wait **0–60 s**. Defaults are **1 / 4 / 15 s**. The patched Helm schema agrees. I checked the supplied measurement rows: eight unrestricted-GC single runs peaked at **151.0–158.2 MiB RSS**. The highest single-run cgroup measurement was **179.9 MiB**. Adding the recorded 134 MiB app gives about **314 MiB**, consistent with the rounded 310 MiB estimate. Four runs give about **547 MiB** on the same estimate. The sizing estimates come from the supplied measurements. A deployed patched API still needs its own measurement. Keep the lab defaults. Docs/18 specifies roughly **100 MiB and one CPU per additional slot** in production and identifies the Helm resource limits and replica setting. Operators should leave thread capacity for probes when increasing the queue.
7. **Tests discriminate.** The base and head results, independent regressions and actual mutation runs are below. The base run copied the PR tests into a copy of base so pytest's configured source path and service conftest could not select head accidentally.
