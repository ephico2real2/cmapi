## Disposition of the four issues

**#746 — approval and visibility.** The owner asked that “adopting a namespace is very easy and promote self services.” D10 retains “one approver of `approver-platform` in each environment” and permits auto-approval only when a rule names adoption. On the recorded run-46 fixture with the required metadata supplied and a within-bounds quota, all three trees listed eight `skipped-key` findings and one `not-adopted`. Base required two approvals, head and the fix required one. A site rule still using `findingCount > 0` required two on every tree. The actual CRC measurement in the brief was 17 findings. The nine-finding fixture is a controlled comparison, not a repeat of that live run. The portal iterates over the complete plan findings. [Design, D10, D20 and #746](head/docs/reviews/2026-11-14-issue-26-adoption/README.md) · [Portal findings](head/cmapi-portal-ui/src/portal/AdoptView.tsx#L287) · [Configuration facts](head/docs/18-configuration.md#L817)

| Excluded built-in code | What the review established |
|---|---|
| `skipped-key` | Ordinary controller and client Update ownership can be informational. Sole ownership by the next applier is the High finding above. Unknown ownership and the migration-manager case already take the kept-key path when the manager data is absent or the configured manager is present. |
| `not-adopted` | D2 says “ServiceAccounts, RoleBindings and SCC grants stay unmanaged.” The notice describes scope. Unreadable counts remain unknown and visible. |
| `adoption-label` | D7 says the provisioner label “stays as it is.” Its recognition list identifies a producer. A recognition miss is reported in the detail. D1 separately checks ownership, tracking and consent. |
| `scoped-only` | D17 excludes a scoped quota from namespace-wide derived figures. The existing scoped CPU test still emits a separate actionable bounds finding when the quota exceeds its bound. |
| `uninterpreted-key` | Capacity interpretation alone says nothing about site bounds. The corrected planner distinguishes a raw key within policy from a raw key violating an actual bound. |

Unknown metadata, a missing required key under D20, a replaced system value and a held policy failure each required the additional reviewer in the dry-plan controls. Duplicate defaults and a key kept because of migration remain counted. Unrecognised future finding codes count by default. The D10 tests for unnamed auto-approval, shipped platform slots and explicit site auto-approval passed.

## Backlog · predates #750

- The planner’s metadata ignore list also skips an **annotation** with the selector label’s name. In an otherwise clean fixture with the validator returning no finding, base and head both required only one approval despite the unknown annotation. The generated annotation rules retain their independent check when enabled. This gap is in unchanged metadata handling. [Metadata classification](head/cmapi/src/cmapi/core/metadata.py#L1473)
- The claim that a requester can never send a **custom** selector label is too broad. When the configured key falls under a site’s allowed team prefix, both base and head accepted it in ordinary create and PATCH dry plans. The reference configuration refused the default key. Reserving a configurable selector in the request API would be a separate compatibility decision. [Key classification](head/cmapi/src/cmapi/core/metadata.py#L907)
