## The change
RFC 9700 section 2.4 says the resource owner password grant MUST NOT be used. Before: the Keycloak client `cmapi-automation` took it, for a local account `bot-user` and for the proofs that sign in 13 LDAP test users. After: `cmapi-automation` is a service-account client (client credentials) whose service account holds the client role `cmapi-onboarding`; no client has `directAccessGrantsEnabled: true`; `bot-user` is removed; the proofs sign a test user in with `head/deploy/oidc-login.py` (authorization code + PKCE through the public client `cmapi-docs`).

## Claims to confirm or refute, exactly

C1. `head/deploy/oidc-login.py`, `login()` and `Session.request()`: the password is sent in exactly one request, the POST to the login form's action, and never in a URL, an argument, an environment variable, an error text or standard output. `LoginError` texts hold no password, code or token. Check `_page_message`: can a page of Keycloak echo the password into the text that the script prints?

C2. Where the password can go. `Session._url()` rewrites only a URL that starts with the issuer's origin. The form's `action` comes from the page. `login()` refuses an action that does not start with the issuer plus `/`. Try to get the password sent to another host or another realm anyway: a prefix trick in the URL (`https://issuer.example/realms/cmapi/../other`, userinfo, a different port), HTML entities, an action in single quotes or with no quotes (the `ACTION` pattern), a second form on the page, `--base` rewriting. Expected: no way. A way is a finding, with the fix and a test in the style of `oidc-login-test.py`.

C3. TLS. The script has no way to turn verification off; with `--cacert` only that bundle is trusted; with `--base http://127.0.0.1:port` it sends the password in clear to the loopback address only, and `Session.__init__` refuses plain HTTP to another host. Check that refusal for bypasses (`localhost.evil.example`, `127.0.0.1.evil.example`, an issuer that is itself `http://`). `urllib` with the `_NoRedirect` handler follows no redirect: confirm it for 301, 302, 303, 307 and 308.

C4. PKCE and state are right: the verifier has enough entropy and the permitted characters (RFC 7636 section 4.1), the challenge is BASE64URL(SHA256(verifier)) with no padding (section 4.2), the state is compared before the code is used, and the code is sent with the same `redirect_uri` and `client_id`.

C5. The cookie handling in `Session.request()` is enough for Keycloak 26's login flow (cookies `AUTH_SESSION_ID`, `KC_AUTH_SESSION_HASH`, `KC_RESTART`), given that it ignores Path, Domain and Secure on purpose. Read the Keycloak source for how the login form's POST finds its authentication session. Say whether sending every cookie to `--base` can leak to another host (see C2).
