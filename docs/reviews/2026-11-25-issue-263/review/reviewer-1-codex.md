## Standards and design read on 2026-11-25

- RFC 3339 §4.1 says “true interoperability is best achieved by using Coordinated Universal Time (UTC).” A date-only expiry has no offset. cmapi’s choice of UTC determines which calendar day to compare with it. [RFC 3339 §4.1](https://www.rfc-editor.org/rfc/rfc3339#section-4.1)
- RFC 5321 §4.5.3.2.6 says a spurious timeout “would typically result in delivery of multiple copies of the message”. SMTP acceptance and a local SQL commit are independent events. [RFC 5321 §4.5.3.2.6](https://www.rfc-editor.org/rfc/rfc5321#section-4.5.3.2.6)
- RFC 8314 §5.3 says “MUAs MUST validate TLS server certificates”. For cmapi’s relay submission the corresponding control is verified STARTTLS before authentication or message transfer. [RFC 8314 §5.3](https://www.rfc-editor.org/rfc/rfc8314#section-5.3)
- Docs/01 specifies “Up to 30 days” per extension and “180 days from creation; longer needs approver-platform”. It requires “no extension in the last 24 hours, and at least two notices sent” and says “Argo CD waits for an operator to confirm the prune”. The table specifies notices at 14, 7 and 1 days and seven days of grace. [Namespace expiration, lines 538–557](https://github.com/ephico2real2/cmapi/blob/9539685/docs/01-design-and-architecture.md#L538-L557)
- Docs/02 says “it lists the namespace for action and tries again the next day” when an expiry guard fails. “Grace starts on the expiry date” and “lasts graceDays including that date”. This distinguishes withholding a request from opening one for a human to approve. [Held deletes and grace, lines 2429–2444](https://github.com/ephico2real2/cmapi/blob/9539685/docs/02-technical-design-v2.md#L2429-L2444)
- Docs/08 §2 describes “the normal delete request through the pipeline” and says “the list, the planner and the check share `utc_today()`”. Its service-test results are the implementer’s record. [Service status, lines 41–59](https://github.com/ephico2real2/cmapi/blob/9539685/docs/08-code-status.md#L41-L59)

**SMTP recovery decision.** A relay can accept a message before the worker can durably record its reply. The patch favors avoiding a duplicate and avoiding false credit toward deletion. An unresolved row can represent an accepted message or a worker that stopped before sending. It needs reconciliation with the relay log. The operator procedure is included in docs/18. This provides at-most-once automatic submission after an ambiguous attempt. An exactly-once guarantee of receipt at a mailbox is unavailable with ordinary SMTP.

## Verdict on the six review questions

1. **Delete and prune.** The worker on head opens an ordinary request. `plan_expiry_delete` supplies the internal requester, runs the approval decision and renders Git removals. `submit` queues approval notification or branch delivery. `pr_checks.py:154` sends a delete to merge, `apply.py:45` excludes deletes, and `watch_sync.py:77–86` enters `awaiting_prune`. Apply-mode deletion requires a recorded operator confirmation. Argo CD mode observes the namespace and relies on prune configuration. A Git protection label matched by `protected.labels`, including `cmapi.net/protected=true` in the examples, refuses planning. The initial scan skips unmanaged live objects and clusters with expiration disabled. An open change holds the delete at scan, with `uq_cr_open_namespace` covering an insertion race. The first finding explains why an unconditional claim about drift was too strong. The two original after-grace tests cover human and automatic approval through prune. The independent submit-only oracle killed a simulated direct removal.
2. **Identity and approvals.** Head has one production caller of `plan_expiry_delete`, in the worker. The HTTP delete route passes the authenticated caller through `plan_delete`, its role check and If-Match. A matching username does not select the worker entry point. Head nevertheless allows an external identity to share worker attribution. The patch reserves it. Nonprod’s shipped policy covers rnd/dev. Staging’s also covers qa/uat, as does the combined reference policy. With passing expiry guards a paused or disabled auto policy leaves the configured human approval rule in charge. The reference `test_expired_namespace_delete` checks the policy outcome, and `test_person_delete_checks_roles_even_for_internal_display_name` checks role enforcement.
3. **Once per date, replicas and leases.** Positive notice thresholds and grace are scoped to cluster, namespace and date. For a committed row, head locks and re-reads before acting. After a date moves, notices for the old date do not qualify the new one. The head planner compares the proposed date with Git before deleting, and branch delivery checks whether the planned folder changed. Head does not provide the same protection for outgoing notices, SMTP acknowledgement loss, or a closed delete request. `JobRepo.claim` uses SKIP LOCKED. `fence` checks the owner and generation with FOR UPDATE, so a superseded generation is rejected before an action. Expiration of a timestamp alone is distinct from takeover. The project already used a transaction advisory lock for daily request IDs. Its existing namespace-write guard is the partial unique index. The hashed advisory lock for expiry actions is new. The patch shares it with extension submissions and propagates lease loss immediately. The original simultaneous-worker test and the added `test_lease_taken_between_namespaces_stops_the_previous_worker` require PostgreSQL.
4. **UTC and the portal.** The service create/set/extend/delete planners, expiration list and daily worker use `utc_today()`. Offset-bearing creation timestamps pass through `utc_day()`. The reference app was the remaining expiry planner using local today. The portal already computes create bounds with UTC getters, and the Expiration tab receives `page.today`. In base and head, OpenAPI requires a string with format `date`, and generated TypeScript declares `today: string`. Only the description changed. A Node check executed the shipped date functions under UTC−12 and UTC+14 and compared both schemas. This was a contract and date-function check, not a browser build. Policy generation intentionally uses the fixed specimen date `2000-01-01` in `core/policygen.py:270`, with no expiry in prod. All three committed instance bundles matched regeneration in UTC−12. The reference tests also cover the 30-day step, 180-day approval boundary, notice thresholds, and inclusive grace.
5. **Mail.** The default transport on head fails the TLS requirement. Its socket timeout is 10 seconds per operation. A definite failure sets `ok=false`, does not count toward deletion, allows other namespace actions to continue, and schedules the next run in 900 seconds. A complete run schedules the next pass in 86,400 seconds. A retry can send again. The proposed delivery ledger distinguishes a definite refusal from an ambiguous acceptance. The original SMTP-off portal behavior remains available.
6. **Tests can fail.** The requested base/head file, reference suite, all four mutants, and independent red/green regressions were executed. Database fixture errors do not establish a mutation kill. Results follow.

## Five-line summary

1. Request changes before merging PR #699.
2. The worker uses the normal delete pipeline. The patch closes gaps in ownership, protection, recent-extension and prune checks.
3. The patch reserves the worker identity and prevents a second delete request for a previously handled expiry date.
4. Verified TLS and a durable submission record protect notices. Ambiguous SMTP outcomes require reconciliation.
5. Four mutants were killed and the patch applied without fuzz. PostgreSQL lock and transaction behavior still needs a database-backed run.
