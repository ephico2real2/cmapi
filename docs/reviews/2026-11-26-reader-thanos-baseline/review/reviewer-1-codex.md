## What the authorization check proves

**Among built-in review APIs, a namespaced LocalSubjectAccessReview is the least privilege that delegates this particular decision to the API server with a caller-selected group list.** A cluster-wide SubjectAccessReview would extend the authority beyond `openshift-monitoring`. A SelfSubjectAccessReview needs no extra baseline grant under default RBAC: `system:basic-user` can create self reviews and is bound to authenticated users. Its implementation takes `userToCheck, exists := genericapirequest.UserFrom(ctx)`. Kubernetes authentication adds `newGroups = append(newGroups, user.AllAuthenticated)`, where `AllAuthenticated = "system:authenticated"`. The self-review spec offers no group override. A live query likewise includes the token's authenticated groups. Either can succeed through COO alone. [Bootstrap policy, release-1.31](https://github.com/kubernetes/kubernetes/blob/release-1.31/plugin/pkg/auth/authorizer/rbac/bootstrappolicy/policy.go) · [Self-review handler](https://github.com/kubernetes/kubernetes/blob/release-1.31/pkg/registry/authorization/selfsubjectaccessreview/rest.go) · [Authenticated group adder](https://github.com/kubernetes/kubernetes/blob/release-1.31/staging/src/k8s.io/apiserver/pkg/authentication/group/authenticated_group_adder.go) · [Group constant](https://github.com/kubernetes/kubernetes/blob/release-1.31/staging/src/k8s.io/apiserver/pkg/authentication/user/user.go)

For an LSAR the authorizer receives `Name: spec.User` and `Groups: spec.Groups`. Validation requires the resource namespace to “match metadata.namespace” and disallows non-resource attributes. The REST handler also enforces the request namespace. The baseline grants only `create` on this review kind in one namespace. Ordinary RBAC cannot constrain the reviewed subject or the hypothetical action in the POST body. Kubernetes documents the create limitation: “You cannot restrict deletecollection or top-level create requests by resource name.” [Authorization helpers, release-1.31 at fa33e07f6a06](https://github.com/kubernetes/kubernetes/blob/fa33e07f6a06/pkg/registry/authorization/util/helpers.go) · [OpenShift release-4.18 at b930000f05a2](https://github.com/openshift/kubernetes/blob/b930000f05a2/pkg/registry/authorization/util/helpers.go) · [LSAR validation, release-1.31](https://github.com/kubernetes/kubernetes/blob/release-1.31/pkg/apis/authorization/validation/validation.go) · [RBAC reference](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#referring-to-resources)

The holder can learn an authorization decision and potentially a reason identifying the granting binding for an arbitrary supplied user, group set and resource action in that namespace. The operation grants no ability to perform the reviewed action. The README's assertion that the baseline reader learns “nothing new” is too strong. It can already inspect cluster-wide RBAC policy, but RBAC objects do not expose the decisions of a webhook authorizer. CRC's reader also gains visibility it previously lacked. The fixed README states this scope. [Kubernetes authorization chain](https://kubernetes.io/docs/reference/access-authn-authz/authorization/)

An allow proves effective rights for the named reader and the two service-account groups. It cannot identify cmapi as the owner of a binding. Another binding to the same reader or to all service accounts can satisfy the check. If the question instead concerns installation of particular cmapi objects, checking exact RoleBindings, their subjects, roleRefs and referenced rules is possible using the baseline's existing reads. CRC would need narrowly named reads, and inspection would answer a different question from evaluating the active authorizer. The baseline itself installs direct ServiceAccount bindings independent of COO.

## Pre-existing behavior and backlog

The ten-minute usage cache and ordinary non-pruning apply both existed on base. The new requirements to honor a current usage finding and retire a previously shipped binding introduce the first and third findings above. The baseline's broad inventory reads, the platform metrics Role's extra verbs, and CRC's external authenticated-users binding are outside the PR's new review grant.

Low, outside changed lines: `KubeClient.served` treats any response below HTTP 400 other than 404 as positive discovery without validating an APIResourceList. This predates the PR. A proxy's login page can therefore yield misleading monitoring diagnostics. The subsequent review still needs a parseable authorization response.
