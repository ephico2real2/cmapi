# Review of cmapi PR #729

**Request changes.** The 4.18 sources support the core interfaces I checked. The release guidance extends the operator evidence beyond its published range, and two configuration details affect whether a real cluster can serve the portal or return capacity metrics. The attached patch corrects the guidance while preserving the shipped policy and application behavior.

## Findings

1. **Medium — A release candidate is presented as the production database path.** `docs/13-crc-deployment.md:9`, `docs/18-configuration.md:26`, audit rows 17–19. The certified catalog entries cover 4.18–4.22 for **1.30.1 and 1.30.2**. Only **1.31.0-rc1** among the entries reviewed lists 4.20–5.0. That says where the bundle can be offered. It does not establish that a GA 1.31 or any later CNPG accepts cmapi’s Cluster on 4.23. The community table also distinguishes supported upstream Kubernetes from tested versions and identifies 1.31.x as preview. Kyverno’s stated v1.20 range, Kubernetes 1.34–1.37, is accurate. A 4.18 site using Kubernetes 1.31 can run the core with the policy engine disabled, but cannot count that as qualification of the Kyverno bundle, reports, or Kyverno-dependent CRC proof. GitOps 1.22.0 likewise has evidence only through 4.22. The patch distinguishes the 4.18+ target, the release endpoints inspected and the one live CRC version. It gives the existing-PostgreSQL and no-Kyverno options. 2. **Medium — The HostNetwork explanation omits which controller sets the label.** `deploy/manifests/components/cmapi/40-networkpolicy.yaml:29-36`, `docs/18-configuration.md:19`, audit row 2. Both CNO versions return early for every IngressController except `default`. With default HostNetwork ingress, the original claim that a cross-node router needs a second peer is incorrect. OVN includes the special namespace’s node addresses in the existing peer. With a HostNetwork shard and a non-HostNetwork default, the shard does not cause CNO to apply that label. Conversely, when the label is present, the selector admits traffic from the included host addresses and cannot identify the router process. The patch qualifies the retraction and the “router alone” wording in the manifest, chart and runbook. The existing peer is correct for the documented default. [4.18](https://github.com/openshift/cluster-network-operator/blob/ae05605cf1e0/pkg/controller/ingressconfig/ingressconfig_controller.go) · [4.23](https://github.com/openshift/cluster-network-operator/blob/1e59ac1595ad/pkg/controller/ingressconfig/ingressconfig_controller.go)

3. **Medium — The Thanos query grant omits a separate discovery permission.** `docs/18-configuration.md:21`, audit row 7. The two monitoring roles both authorize the proxy’s check. Neither includes `routes.route.openshift.io`. With no `thanosUrl`, `cmapi/src/cmapi/capacity/thanos.py:37-49` first reads the named Route and raises `MetricsUnavailable` if that read fails. Binding just the documented role can therefore leave the reader unable to query usage on either release. The CRC reader YAML in this snapshot grants neither the Route read nor the monitoring role. The patch gives both prerequisites, scoped to each cluster queried with `usage.source: thanos`, and the explicit URL alternative. It does not assume dependent PR #726 has landed or require monitoring privileges on clusters with usage disabled. [4.18](https://github.com/openshift/cluster-monitoring-operator/blob/87b50fc0c80f/assets/cluster-monitoring-operator/cluster-monitoring-api-role.yaml) · [4.23](https://github.com/openshift/cluster-monitoring-operator/blob/e2ca4944ea4a/assets/cluster-monitoring-operator/cluster-monitoring-api-role.yaml) · [4.18](https://github.com/openshift/cluster-monitoring-operator/blob/87b50fc0c80f/assets/cluster-monitoring-operator/cluster-role-view.yaml) · [4.23](https://github.com/openshift/cluster-monitoring-operator/blob/e2ca4944ea4a/assets/cluster-monitoring-operator/cluster-role-view.yaml)

4. **Medium — The deployment inventory omits prerequisites for specific workflows.** Audit rows 5, 6, 16 and 17. The CRC push path needs the integrated registry’s external Route and a token authorized to push (`deploy/release-crc.sh:18,73-96`). The API import path needs ImageStreamTag reads but can operate without that external Route (`deploy/crc-image.sh:41,59-66`). `deploy/crc-backup.sh:45` uses resource metrics via `oc adm top pod` to check backup headroom. The Helm database template also asks CNPG for a PodMonitor when service monitoring is enabled. Both CNPG CRDs examined expose and deprecate this switch. Finally, the CRC realm-import manifest needs the site’s RHBK operator serving `k8s.keycloak.org/v2beta1`; installations using an existing realm can leave realm import disabled. The patch records each dependency and identifies the realm operator’s cross-release range as unverified. [4.18 registry guide](https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html-single/registry/registry) · [4.18](https://github.com/openshift/cluster-monitoring-operator/blob/87b50fc0c80f/assets/metrics-server/api-service.yaml) · [4.23](https://github.com/openshift/cluster-monitoring-operator/blob/e2ca4944ea4a/assets/metrics-server/api-service.yaml) · [CNPG Cluster CRD](https://github.com/redhat-openshift-ecosystem/certified-operators/blob/e32946f01859/operators/cloudnative-pg/1.30.1/manifests/postgresql.cnpg.io_clusters.yaml)

5. **Low — A default feature gate is described as default authentication.** `docs/18-configuration.md:23` and the new test docstring. The 4.18 gate also includes the default HyperShift profile. By the audited 4.22 pin it is already on in the default profile. Even at the 4.23 pin the default authentication type is IntegratedOAuth. The test exercises a site that *configured* direct OIDC. The patch corrects the descriptions. [4.22 gate](https://github.com/openshift/api/blob/5e2e49130034/features/features.go) · [4.23 authentication default](https://github.com/openshift/api/blob/7a9ff1ebb38f/config/v1/types_authentication.go)
