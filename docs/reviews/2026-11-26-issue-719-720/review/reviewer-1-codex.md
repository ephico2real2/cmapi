## Disposition of the four claims

1. **Universal inverse parity is refuted.** The measured differences above affect both shipped guards and configurable rules. The ordinary undo of a create *does* refuse a protected Namespace and requires two slots for an old dev Namespace. The ordinary update inverse reads the restored tier, team and current cluster labels, including when the parent team differs.
2. **Only the exposure fact changed on forward requests, but the intended last-bound scope is refuted.** The only executable change in the forward planner is the calculation of `raised`. I compared the base expression and head helper for all 256 old/new pairs formed by independently assigning each of the two keys absent, 0, 1, or 2. The shipped dev-update requirement changed in 57 pairs. Each change was attributable to a removed key. The sibling-quota planner tests establish why removal of a key from one map can still be a false positive for namespace exposure. Removing the actual last bound was detected in all four single-quota tests covering both keys and directions.
3. **The coordinator's clean small-dev ruling is confirmed.** Forward and inverse both returned `dev-create`, `auto:baseline-rnd-namespace` and zero slots with fresh fitting capacity, no warnings, region `us-central` and an available team allowance. “The revert is a new request through the same approval rules” supports that result. A dated or warned target has different inputs to those same rules. [Lifecycle design](head/docs/01-design-and-architecture.md#L260) · [Shipped auto-policy](head/examples/instances/nonprod/approval-rules.yaml#L68)
4. **Independent tests distinguish base, head and mutants.** Database-backed red/green remains unverified here. The local tests exercise the real forward planner, renderer, revert worker through its call to submit, and shipped rule engine. Fake Git, capacity, Kubernetes and validator inputs make the comparison reproducible. They do not exercise migration, row locking, queue retry, the submit-time daily count, Git delivery or cluster pruning.

1. Request changes for missed inverse approvals and a forward exposure false positive.
