# Reviewer 1 · cmapi PR #725

**PostgreSQL verification blocked.** The sandbox denied TCP connections to the designated database at `127.0.0.1:55432` with `Operation not permitted`. The database fixtures failed before their assertions. All database results below distinguish source inspection, local tests and the PR author's measurements. No SQLite or cluster was used.

**Decision — request changes.** Head can approve a request whose hold expired after another request took the room. It can also reject a forward create that fits exactly. Eleven regression assertions failed on the supplied head and passed with the [review patch](r1-outputs/fix.diff). I applied it to a fresh [copy of head](r1-outputs/fixed/) and compared it with the tested tree, excluding `examples/`. The supplied code snapshots have no TokenSave index, so source references below point to the files inspected directly.

## Design

> Placement takes a reservation inside the same transaction as the capacity check, under a per-cluster advisory lock, so concurrent requests see each other. The reservation ends when the namespace's ResourceQuota appears in cmapi's watch cache of that cluster. Committed quota counts it from then on, so it is never counted twice. It also ends when the request is rejected, cancelled or times out.

The schema describes the deadline as “the approval timeout once submitted”. The lifecycle requires “The count is met (auto or :approve) and capacity still fits”. The PR deliberately renews the term on progress and allows a person to approve an unknown capacity result. The findings below concern known capacity or the accounting used to calculate it. ## Lifecycle, lock and revision checks

- **Terminal release.** Seven database-independent cases exercised the real `RequestRepo.move` dispatch and verified the request ID, destination reason and caller's session for rejection, cancellation, approval timeout, failure, sync success, supersession and sync failure. Sync failure gives up the reservation while retaining the namespace lock. A later revert from that state already has no hold. A reservation's own expiry is a timestamp condition, separate from the request's `timeout` state. Head filters out expired rows immediately and stamps them on a subsequent reservation. The PR's integration tests check stored rows and the watch's ADDED path. [Lifecycle tests](r1-outputs/fixed/cmapi/tests/service/test_capacity_reservation_edges.py) · [PR service tests](head/cmapi/tests/service/test_capacity_reservations_62.py)
- **Two submits.** For fresh capacity, stable watch data and one available slot, the locked head submit rereads holds, inserts the request and writes its hold in the same SQLAlchemy session. The key is the signed first eight bytes of SHA-256 over `cmapi-capacity:{cluster_id}`. PostgreSQL releases `pg_advisory_xact_lock` at transaction end, including rollback. The ordinary eight-submit test also takes the pre-existing daily request-ID lock, so it cannot by itself detect removal of the cluster lock. The patch also exercises two simultaneous submits for one slot. It adds a direct transaction test in which a different cluster proceeds, the same cluster times out, and acquisition succeeds after commit. The SQL/key test and both lock mutants ran locally. Actual waiting and transaction visibility await PostgreSQL. [Request ID and cluster lock](head/cmapi/src/cmapi/core/db/repo.py) · [Commit and rollback](head/cmapi/src/cmapi/core/db/__init__.py) · [PostgreSQL lock reference quoted in the PR](head/docs/reviews/2026-11-26-issue-62/README.md#sources)
- **Revision audit.** `REQUIRED_REVISION` is 0011, and 0011 descends from 0010. The newest-migration assertion and the updated “0009 needs 0011” readiness assertion passed. Searching all of `tests/service` for `0010` found historical usage-table documentation, a fabricated future revision in a test that pins its requirement to 0003, and unrelated request-ID strings. There was no stale literal expecting the production head to equal 0010. The patch adds a direct 0010 readiness check. Both the existing empty-database up/down/up and the new populated-schema round trip require PostgreSQL. ## Existing behaviour and verification limits

Base already sizes ordinary forward changes against the quota in Git, permits human decisions with unknown capacity, and serializes same-day submits through `next_id`. These are separate from the PR regressions. The capacity view's omission of open holds is already tracked as low-priority backlog #723. The fixed handoff uses each reader's watch while the request holds capacity. Terminal release still follows the lifecycle, and a replica's view of an external or already-completed change depends on its watch catching up. [Base planner](base/cmapi/src/cmapi/core/pipeline.py) · [PR design decisions](head/docs/reviews/2026-11-26-issue-62/README.md#decisions-and-why)

The patch changes 0011 in place on the assumption that this PR is unshipped. An installation that has already run the PR's 0011 would need a follow-up migration. The backfill samples stored plans while blocking writes to change requests. Old binaries still running after that transaction can write requests without reservations. The serialized-admission guarantee requires the new writers. PostgreSQL lock duration during backfill and delayed delivery, a rolling deployment, and real cluster watch propagation were not measured here.

## Five-line summary

1. Request changes for incorrect watch accounting, expiry recovery, lock ordering and migration of live requests.
2. Terminal-release dispatch and the per-cluster transaction-lock call passed local checks.
3. Same-state retries can renew head's hold indefinitely, and head can reject a forward create that fits.
4. Eleven head regression failures passed on the patched copy, and nine mutants were detected.
5. PostgreSQL must still verify concurrent admission, transactional rollback and the populated 0011 up/down/up.
