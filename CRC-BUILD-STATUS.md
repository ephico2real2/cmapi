## Decisions taken (owner to review)

1. The reference package moved to `cmapi/src/cmapi` with symlinks left at the documented paths.
2. SQLAlchemy with psycopg 3, synchronous, instead of the asyncpg named in `docs/02`: the reference modules, the Git and cluster adapters and the worker are synchronous, and FastAPI runs sync handlers in a thread pool. Not yet reflected in `docs/02`.
3. Delivery: `argocd` is the default in the code and the chart, as the design says, and the coordinator decided (#63, 2026-11-05) that CRC runs it: `crc.yaml` selects `delivery.mode: argocd`, `argocd.namespace: cmapi-argocd`, and acknowledges nothing. `apply` (the worker checks that Git `main`'s folder equals the approved plan, server-side applies that plan as the `cmapi-deliverer` identity contained by an admission policy, confirms by a read, holds deletes for `POST /admin/prune:confirm`) stays in the chart and renders only with `delivery.hubDeliverer.acknowledgeDirectWrites`. Fable's recommendation for `apply` on CRC and Codex's counter-argument are left as written in `docs/reviews/2026-11-05-pr40.md`. Nothing has run on a real Argo CD; its objects are the thin slice's design step. `docs/01` and `docs/02` stay as they are.
4. Two reference modules changed with tests: the kill switch reports `paused` as the auto-approval fallback; `ListQuery` gained `context` so a cursor is bound to a caller's scope without filtering rows.
5. Realm `cmapi` in the existing Keycloak through a `KeycloakRealmImport` plus one placeholder Secret in namespace `keycloak` (`cmapi-realm-secrets`, generated), the pattern the existing imports use. The import carries the service accounts' realm-management roles and every scope it names (Opus measured on community Keycloak 26.0.7 that listing scopes suppresses the defaults; RHBK's operator import is still unrun). Mutable parts (user profile, group-to-role mappings, LDAP federation, local test users) converge through the `cmapi-realm-admin` service client in the realm sync Job. LDAP federation is configured only when Secret `cmapi-ldap-bind` (`bindDN`, `password`) exists in `cmapi` (#34, the owner's step); until then local users `ola`, `amy`, `opal`, `bot-user` with generated passwords (Secret `cmapi-test-users`). `cmapi-cli` has no password grant; `cmapi-automation` is confidential.
6. The Gitea stand-in uses basic auth for the bot (`CMAPI_GIT_USER`/`CMAPI_GIT_PASSWORD`) over plain HTTP inside the cluster (#59, open); the GitHub adapter uses a token and has never been exercised (#61).
7. Kyverno CI checks run in the worker's `pr_checks` job and are posted as commit statuses (`ci/kubeconform`, `ci/kyverno`, `cmapi/check`) that branch protection requires; the worker therefore posts its own required checks (#60, open). On a real GitHub the same contexts come from Actions and the cmapi check reads `GET /requests/{id}/approval-status`.
8. Migrations run as an initContainer on the api and the worker (serialised by an advisory lock, `lock_timeout` 30 s so a migration cannot queue every reader behind it, a wait of up to 540 s for a database that is not listening yet, under helm's 10 m), and `/readyz` waits for a schema at or past `REQUIRED_REVISION`. A revision this code does not know counts as past only by the repository's convention (four digits, a higher number); a known revision on a divergent branch and anything else are refused, by `/readyz` (503) and by `cmapi-migrate` (exit non-zero). The `cmapi-capacity` console script is removed until the component exists (`docs/08`).
9. Job leases carry a fencing generation: a worker whose lease was claimed again while it was paused cannot commit, and `JobRepo.fence()` before each side effect (open, close, merge, apply, delete) holds the job's row until commit. Cost: the heartbeat's `UPDATE` waits on that row, and a handler wedged after the fence keeps the job until the process dies, which `CmapiWorkerNotLooping` reports.
10. The prune is bounded. Only two things are waits (the attempts reset, the reason on the request once): the cluster's reader not connected yet, and the namespace still present. Every other failure takes the worker's five attempts and then moves the request `awaiting_prune` to `sync_failed` (a new edge in the reference module `core/lifecycle.py`), where `:retry` enqueues the prune again and `:revert` restores the folder. An unmanaged namespace at prune time goes there at once.
11. The release is atomic: `helm upgrade --install --atomic --cleanup-on-fail` by default, so a failed first install rolls back instead of leaving "no deployed releases"; every generated Secret, the realm import and its Secret carry `helm.sh/resource-policy: keep`, so the next run reuses them. `RELEASE_ATOMIC=false` keeps a failed release's pods for inspection. A `-dirty` tag is pushed every time; a clean tag already in the registry is reused.
12. The migrate initContainer mounts the trust bundle and sets `PGSSLROOTCERT` when `trustedCA` is set, so an external TLS database verifies against the same bundle as the main containers (CNPG's in-cluster database does not need it).
